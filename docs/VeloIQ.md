# VeloIQ 2.0 — how it works

Written 18 October 2026, at the point the app reached usable form; updated the same night after the plan, library and print work, on 19 October after the coach, day-note and sync-security work, and on 20 October (seven-pattern strength with gym equipment, recording plausibility, update checks, the record of what was done). This is the reference for anyone (including a future Claude session) who needs to understand the app without reading the code: what it is for, how it is built, how the training engine thinks, and the standing requirements that shaped it.

## What it is

A personal cycling-training app for a masters road rider, run entirely in the browser as an installable web app (PWA). It plans training around the rider's own data, sends rides to a Garmin Edge, reads back what was done, and recommends strength, mobility and walking alongside the riding.

Live at https://zooharris.github.io/ride/ (source: github.com/zooharris/ride). Anyone can open the address and connect their own Intervals.icu account; each install holds only its own person's data.

## The one outside service

Garmin's developer programme is closed to individuals and Apple Health has no web API, so **Intervals.icu is the single pipe**:

- Workouts sent from the app become Intervals.icu calendar events, which Intervals.icu pushes to Garmin Connect and so to the Edge or watch. Rides carry power/HR steps; walks a HR target (type Walk); strength sessions go with one step per set ending on a lap press (`- Press lap <name> <reps> reps <load> <estimate>`, numerals; a range as "8 to 10"), timed rests (60/90/120 s by effort) and timed holds, sets as repeat blocks; mobility with timed holds, a step a side (`sessionSteps()` in intervals.ts). Intervals.icu carries no exercises, so the device shows step text only — no rep counting. **Interim (19 Oct 2026): strength and mobility are sent typed as Ride** (`SESSION_EVENT_TYPE`), because Intervals.icu passes step text to Garmin for Ride workouts and drops it for every other type — proved 19 Oct with a one-off probe (two identical workouts typed Ride and Workout, since removed from Settings) on an Epix Pro Gen 2: identical steps show their names in a bike activity and only "Go" in a strength one. The rider follows them in a copy of the Indoor Bike profile (his is named "VeloIQ": HR, laps, lap time, timer, HR zone, calories; each set is a lap). Confirmed working end to end on the wrist 19 Oct. A feature request is with Intervals.icu; when text travels for other types, switch the constant to WeightTraining/Yoga.
- Any activity recorded to Intervals.icu — from the Edge, a watch, a manual entry — comes back to the app on Sync, whatever device recorded it. The app never assumes a particular device.
- Wellness (HRV, sleep, resting HR) comes from Intervals.icu too, from whatever writes it there (Garmin, Oura, by hand).
- FTP, threshold HR and max HR are kept in step both ways.
- **Sync across devices** (`src/data/devicesync.ts`): the app's own data (profile, settings, plans, calendar entries, workouts, day notes) lives in a private note in the rider's own Intervals.icu calendar (31 Dec 2099, gzip+base64 — compressed, not encrypted; only the rider's Intervals.icu login or API key reaches it). **The Intervals.icu and Claude API keys never go into the note** (`SECRET_SETTINGS`): each device keeps its own, pasted once; a restore from the note keeps the keys the device already has. The file backup does carry them, by design, for a one-step restore. **The note can be encrypted** (`src/data/notecrypto.ts`, WebCrypto only): a random AES-256-GCM data key encrypts the payload and is wrapped twice, under a key derived from the rider's passphrase and under one derived from the normalised answer to a question the rider set (PBKDF2, 300k iterations); both wrappings travel with the note. The data key and lock live in local-only settings (`noteKey`, `noteLock`). A device that cannot open the note enters a `locked` state (question shown in Settings and a banner on Today), syncs nothing in either direction, and unlocks with the passphrase or the answer. Changing the passphrase re-wraps the same key, so other devices keep working; turning encryption off rewrites the note in the clear. The rider chose a challenge question over a recovery key, for simplicity, knowing the answer is only as strong as its guessability. Every write stamps `updatedAt` and every delete leaves a tombstone (Dexie hooks in db.ts, `untracked()` for applying remote records); each device merges with the note on launch, on return to the foreground (≤ once a minute), after every Intervals sync, and ~4 s after any local change (`notify()` → `schedulePush`). Newest record wins, deletions carry, unstamped legacy records union. The same note is the backup a new device restores from; a file backup remains. No server; each account's note is its own, so nothing mixes.

Map tiles come from OpenStreetMap (free, no key). Claude (Anthropic API) is optional and off unless a key is entered.

## Technology

Vite 5 + Preact 10 + TypeScript. IndexedDB via Dexie for storage. Hash routing. vite-plugin-pwa for offline. Leaflet for maps. Vitest for the engine, sync, encryption and coach tests (69). Hosted on GitHub Pages from `main` via GitHub Actions; every push deploys in about two minutes. No server of any kind.

```

    zones.ts        Coggan power zones; Friel-style HR zones mapped by zone position

    generate.ts     ride session generators by type (endurance … VO2max, tests)
```

## Data model (IndexedDB, one database per browser profile)

- **profile**: name, FTP, LTHR, max/resting HR, weight, units, default basis (power/HR), masters flag.
- **settings**: key/value — Intervals credentials, Claude key, `plans` (the list of named plans), plan request, view preferences, tour state, `deviceSync` state and `deviceId` (local only).
- **tombstones**: `${table}:${id}` + time, for deletions to carry across devices.
- **workouts**: hand-built (`source: 'mine'`) and generated copies (`source: 'generated'`); the library itself is code.
- **planned**: calendar entries — date, workoutId, basis, status (planned → sent → completed, or missed), Intervals event id, matched activity id, planId if a plan created it.
- **rides**: every activity from Intervals.icu with the app's own TSS; `sport` is ride | strength | mobility | walk | other.
- **wellness**: per-day HRV, resting HR, sleep, weight.
- **dayNotes**: per-day rider note (`text`) and `badWellness` flag; synced and backed up with the calendar. `trustedWellness()` in store.ts drops flagged days, so `data.wellness` everywhere is already the trusted set (`wellnessAll` is the raw one).
- **streams**: cached recordings (time, power, HR, cadence, distance, altitude, speed, temperature, GPS).

Workout model: a workout is blocks of steps; each step is a duration and a target as a *fraction of threshold* (plus an optional cadence note). The same workout renders as %FTP or %LTHR depending on the basis it is sent on, because Garmin accepts one target type per workout. VO2max and above are power-only (HR lags too much for short efforts).

## The engine

**Load.** TSS = seconds × IF² / 36 from power; hrTSS from HR zones when there is no power; strength from planned/logged effort (RPE² × 50/49 per hour); walks from the HR target as Intervals.icu would credit them; mobility a flat 8/h. Fitness (CTL) is a 42-day exponential average of daily TSS, fatigue (ATL) 7-day, form = fitness − fatigue.

**Assessment** (`assess()`): from rides, wellness and the power curve it derives fitness and ramp rate, weekly hours and TSS, longest ride, aerobic decoupling and efficiency trend, power profile by duration, how the rider responds after strength / long rides / hard rides (from wellness and next-day output), whether FTP looks fresh, stale, likely higher or likely lower (eFTP signal), compliance, and the limiters. Every value carries a confidence (none / thin / good) and a sentence of evidence.

**Demand** (`demand()`): the goal turned into numbers — for an event, the estimated duration and intensity, the TSS of the day, the fitness needed, the longest training ride wanted, and the emphasis (durability / threshold / VO2 / recovery). Other goals (FTP, endurance, weight, general) have their own demand shapes.

**Planning** (`generatePlan()`): the rider gives only **hours per day**, where they can ride each day (outdoors / indoors / no bike), their equipment, and standing commitments (a day pinned to a ride, strength, a walk, mobility or rest, honoured every week; a pinned day is kept clear of anything else). The planner decides, for every other day, ride / strength / mobility / walk / rest:

- Phase sequence from weeks available and the goal: base → build → peak → taper, proportioned by what the goal rewards and what the data flags as the limiter.
- Sessions generated to fit each slot (an endurance ride sized to the slot, intervals by phase and progression), named and explained.
- An allocator with soft costs, scaled by the rider's measured recovery responses — nothing is a hard rule. A hard ride the day after strength costs more if the data show that rider recovers poorly from lifting, less if they recover well. Two long rides in one week are allowed when two long slots exist, the goal rewards durability, and the after-long-ride penalty is low.
- Ramp capped (4 fitness points a week for a masters rider, raised with recovery evidence). Recovery rhythm starts at every third week for masters; fatigue evidence inside a week discounts load and puts easy days after hard ones.
- FTP tests only when the FTP looks stale.
- Strength count and level by phase; mobility after the long ride and after strength; walks for windows under 45 minutes or no-bike days when a treadmill or outdoor walking is available.
- Output: weeks of sessions with reasons, a fitness projection, verdict (on track / close / short), advice, and a list of decisions in sentences. Plan weeks start on Monday; nothing before today.

**Adaptation**: every day after a sync the plan is fitted again to the latest data **within its own layout** (`layout` in PlanRequest: the weeks and phases saved on the plan as `weeks`, worked out once from the plan's first week and saved for plans made before they were kept). The phases never shift; weeks already begun, the week in progress included, are left as they are on the calendar (the week in progress still counts toward fitness and block progress), and the re-check offers changes from next Monday. Laying the plan out afresh each day, as before 20 Oct, moved every phase boundary as the weeks went by and produced over a hundred suggestions. The fitted plan is diffed against the calendar, and last week is reviewed (done / missed / over-cooked). Only changes that matter are offered (`sameSession()`): a ride that is the same session (name apart from its length, same family) changed by under 10 minutes and 10% in length and under 5 TSS and 10% in load counts as unchanged, since the daily rebuild otherwise moves every ride by a few minutes. Each change is a tick box: changes to plan-made sessions are ticked, suggestions touching sessions the rider replaced, moved or added by hand (`userEdited`, `movedFrom`, or no `planId` on the calendar entry; `userAdded` on the change) are unticked; only ticked changes apply, unchanged sessions are kept. Cancelling a plan removes only future, undone sessions the plan created.

**Pairing** (`pairRecordings()` in syncService.ts, tested): on every sync a recording is matched to its planned session in two passes — the certain matches first (Intervals.icu's `paired_event_id`, then the same day and name; the watch names the recording after the workout), then the same day and kind for what is left — so a strength session recorded as a ride is never taken for the day's planned ride. **Every pass needs a believable recording** (`plausibleFor()`, 20 Oct 2026): at least five minutes and at least a fifth of the planned time, so an accidental watch-button press (a 25-second Garmin "Cardio", type Workout, on the day of a 40-minute strength session) completes nothing, while a ride cut short still pairs as a partial one. A session marked done from a recording that no longer counts (too short, or deleted from Intervals.icu) returns to to-do (missed if the day has passed) on the next sync; sessions logged by hand (`loggedSeconds`) stay done. The rules live in `applyPairing()` (syncService.ts), which Sync runs on fresh recordings and the app runs once at launch on the last two weeks it already holds (`recheckMatches()`, no network needed), so a rule change or a deleted recording takes effect without a Sync. The rider can also undo a match by hand: **This was a different workout** in the result box at the top of the recording page (`unmatchRecording()`) puts it back to to-do (missed if past), adds the recording to the session's `notActivityIds` so no pass pairs it again, leaves the recording as an extra activity, and restores its original Intervals.icu type if the app had relabelled it (`relabelled` on the calendar entry records the original). A recording paired to a planned walk, strength or mobility session takes that kind whatever type the device gave it (a treadmill walk often arrives as a Run; a Run slower than 7 km/h is a walk anyway), is scored for it (Intervals.icu's ride-based load discarded), and **its type is corrected in Intervals.icu** (`updateActivityType`, PUT /activity) to WeightTraining / Yoga / Walk — again on any later sync if it drifts back, e.g. after an edit in Garmin Connect, which re-sends. Garmin Connect keeps its own label. The calendar then shows one row, marked done with the recorded time, load and heart rate, and a link to the recording.

**The record of what was done** (`src/engine/record.ts`, `DoneRecord` on the calendar entry as `done`): captured when a session becomes done (matched or logged by hand) as a snapshot of the plan's exercises, sets, reps and holds (walks: minutes and pack), assumed done as planned (`editedAt` absent). The rider edits it on the recording page (`DoneEditor` in src/ui/DoneRecord.tsx): change an exercise to another from the app's list (strength by pattern for the rider's equipment, or the stretches), sets, reps, weight (a number in the rider's units, stored with its unit), hold seconds, skipped, add or remove rows; Save / Cancel / Reset to planned. It syncs across devices with the calendar. **Effort** (1–10, `rpe`) is asked on the same page; for strength it sets the session's training load (`recordTss()` = the hand-log formula, applied on every pairing since rides are re-fetched), because heart rate under-reads lifting. **Last time**: `lastDone()` finds the latest weight used for an exercise (by library id, else name; skipped entries ignored); upcoming strength sessions show "Last time: 35 lb · 3 × 10 · date" per exercise and the Garmin step text gains "last 35 lb" (`setLastWeightLookup()` in intervals.ts, set by the store). **Intervals.icu**: the record is written into the activity's description (`recordText()`, ending "— VeloIQ") only when the description is empty or the app's own earlier text, so the rider's notes are never overwritten; a hand-logged session's manual activity carries it from the start, and its id is kept as `manualActivityId`, the only activity **Undo: not done yet** may delete. The coach's session line includes what was actually done.

**Compliance** (`scoreRide`, `analyseRide`): a ride matched to its planned workout (by Intervals event id, else date + kind) gets a verdict and an interval-by-interval comparison laid along elapsed time from the recording.

**Readiness**: HRV 40%, sleep 30%, resting HR 15%, form 15%, each against the rider's own 2-week baseline → a score and a band (go / ease / easy / rest). The advice line under it (`readinessAdvice()` in Today.tsx) is written for what is actually on the day — strength only, walk or mobility only, nothing — not an assumed ride.

**Day notes and the coach.** Two cases, kept distinct: (1) the watch was not measuring (sleep mode off, on the nightstand) → the rider ticks "not real measurements" and the day's wellness drops out of readiness and of every average; (2) the numbers are real but explained (a late glass of wine, a flight, a cold coming on) → the rider just writes the note; nothing drops. The coach reads the rider's notes before the numbers and is told they outrank them. The daily note is built from **everything on today's calendar** (`describeSession()` in coach/claude.ts: kind, size, exercises, done/not done, hand-added or plan-made) and is remade when the day's calendar or note changes; it gets three months of day notes so a recurring cause can be named. The post-sync review gets two weeks of notes.

## Screens

- **Today**: getting-started checklist (first run), today's ride with Send to Garmin, other sessions, next up, readiness with explanations and, under it, "Your note about today" (text + the not-measured switch; collapses to a one-line summary with Edit once saved), fitness chart with form bands, the plan's daily re-check (per-change tick boxes), the coach review. The app always opens here.
- **Plan** (its own tab, "Plan my training"): the list of plans (name, dates, current / upcoming / finished; Re-check on the current one, Print and Cancel per plan); the new-plan form with name, start date, goal, your week (hours; Outdoors / Indoors / No bike; a commitment per day: App decides / Always a ride / strength / walk / mobility / rest), equipment, masters toggle → result with verdict, projection chart with shaded form bands, decisions, weeks; Put on calendar / Discard. Plans never overlap; a clash is refused with the reason. Plans without an event end on a recovery week.
- **Print** (`#/print/<planId>`): US Letter landscape with its own `@page` rules; calendar layout (one row per week, one column per day, done/missed marks, recovery weeks tinted, weekly hours and TSS) or list layout; 12 weeks comfortably and 16 tightly on one page, longer plans paginate with the header repeated. Verified by printing to PDF in headless Chromium.
- **Calendar**: list (two weeks) or month; + Add any kind; ⋯ on any session to replace it with another workout of any kind, move it to another date, or remove it (confirm); Send N to Garmin. A session's own page also has "Remove from the calendar" (shared `removePlanned()`; a sent session comes off Intervals.icu and the Garmin, a done one keeps its recording).
- **Library**: Rides with a filter toolbar (search, Type menu, Length menu, Sort menu; dropdowns on a laptop, bottom sheets on a phone); Strength / Mobility / Walks ready-made for the rider's equipment; My … sections; "New workout" → chooser → ride, strength, mobility or walk builder, each showing estimated TSS live. Walks carry a heart-rate target (% of max, shown in bpm; a low of 0 = no minimum, the Recovery preset). Recovery-family rides and any step built with a low of 0 enforce no floor (`noFloor` on the step; sent to the device as 10% FTP / 20% LTHR because Garmin needs two ends) and can be sent to the Garmin as walking workouts (Intervals.icu type Walk, target as % LTHR).
- **Ride names**: every library ride is named for a place (src/library/names.ts): where you would turn around on an out-and-back from Old Town Herndon at the ride's intensity. Outdoor-shaped rides go west on the W&OD (long rides = trail towns, interval rides = roads off the trail), core rides go east toward Washington, indoor rides take the loops near home; tests keep plain names. The descriptive name is the subtitle and goes to the Garmin with the place name. The file lists unused names for future rides.
- **Activities**: list or month; detail with verdict, route map, stacked interactive charts (shared cursor with the map; mouse or touch), time in zone, numbers with descriptions.
- **Settings**: Intervals credentials + connection checks; your numbers; zones; week starts on Monday or Sunday (calendar, lists, plan rows and printout follow); coach key and auto-review toggle; across your devices (last merge, Sync now; "Replace this device with the note" was removed 19 Oct at the rider's direction as a single-confirmation data-loss control the merge makes unnecessary); encryption of the note (set up / unlock / change / turn off); file backup.
- **Updates** (also): each build publishes `version.json` (its build time); the app compares it with its own at launch, on return to the front (`visibilitychange`, `focus`, and `pageshow` for an iPhone home-screen app resumed from the background) and every 15 minutes, and shows the banner when the server has a newer build even if the service worker never noticed. If Reload finds no newer worker waiting, it unregisters the service worker, clears its caches and loads the page fresh (IndexedDB untouched).
- **Updates**: a new build waits until the rider presses Reload on the banner. The app looks for one at launch, every 15 minutes, and whenever it comes back to the front (at most once a minute); Settings shows when the running version was built, in local time, with Check for updates. Reload (`applyUpdate()`) asks the server again, waits for the newest build to install, then switches to it, so one press lands on the newest however many were published since the banner appeared; the button shows Updating… meanwhile. Commits that touch only `docs/`, `art/` or Markdown do not publish a build (deploy workflow `paths-ignore`).
- **A done session** opens its recording ("how it went"): the result box at the top (Done / the ride's verdict against the planned session, time and load against plan, a warning when the recording is under a fifth of the planned time, and **This was a different workout**, or **Undo: not done yet** for a session logged by hand); **What you did** for strength, mobility and walks; **What was planned** folded open in place (exercises, or the ride's steps), with a link to the session in full; then the recording's charts (hidden for recordings under two minutes and for hand-logged sessions) and numbers. Below the numbers, **About this activity**: rename (PUT name to Intervals.icu), **What it was** for an unmatched activity (an `ActivityEdit.kind`, applied over the device's type on every download by `applyKindEdits()`, with the Intervals.icu type corrected too), and **Leave out of training load** (`excluded`: `applyLoadEdits()` sets `tss` 0 and keeps `uncountedTss`). An unmatched recording also offers **Was this a planned session?** (`matchByHand()`, sessions within seven days not done, same kind first): it sets `matchedByHand`, which `pairRecordings()` honours before every other pass, whatever the day, name or length; This was a different workout clears it. Unplanned strength, mobility and walks get **What you did** and effort (`ActivityEdit.done`, `rpe`; effort sets an unplanned strength session's load); `doneHistory()` merges these records with the calendar's for Last time. Activity edits live in their own table (`activityEdits`, keyed by activity id), synced across devices and backed up like the calendar, because activities themselves are re-downloaded on every Sync. At the bottom, **Delete this activity** (`deleteRecording()` in src/sync/records.ts, after a confirm): deleted in Intervals.icu first (if that fails nothing is deleted, since it would return on the next Sync), then locally with its streams and power curve; a session it completed goes back to to-do, a hand-logged one is undone. Sync also removes local activities in its window that Intervals.icu no longer has. The session's own page is for planning; once done it shows one line, "See how it went ›", or for a hand-logged session the record and the undo.
- **Help**: one section per screen, the numbers explained, backup and other devices, troubleshooting.

## Standing requirements (from the rider)

- Every number gets a clear descriptive label; charts have labelled axes and hover explanations.
- Any delete asks "are you sure?"; every place a change can be abandoned has Cancel / Reset.
- The planner assesses the rider's own data; no blanket rules; assumptions questioned.
- The rider specifies only hours and constraints; the app decides the kind of session.
- Strength sessions name real exercises, sets, reps and load for the rider's equipment, covering seven patterns (squat, lunge, hinge, push, pull, carry, rotate); equipment options include barbell, pull-up bar and dip bars (no cable machine), gym versions leading when present; mobility sessions name stretches and holds; walking is a session kind.
- No stopgaps or templates.
- Any calendared session, plan-made or not, can be replaced (any kind), moved or removed by the rider; the plan keeps the rider's change and may only suggest otherwise.
- Library rides have unique, memorable place names (Virginia, around the W&OD from Herndon) with the descriptive name as subtitle; the library offers a range of durations up to six hours and can be filtered by length.
- No device assumed; Intervals.icu is the single source of completed activities; app-logged sessions are written back to it.
- Must run without Claude; Claude is optional and never changes the plan without the rider's OK.
- The coach and anything that reasons about "today" take the calendar as the plan: every session on the date, however it got there.
- Secrets (API keys) never leave the device in the sync note; the rider is security-conscious about anything stored outside the device, and wants features kept simple (chose a challenge question over a recovery key).
- Giveable to others with no mixing of data.
- Must look like a professionally designed, commercially available app.
- The rider never touches git; API keys are pasted into the app, never shared in chat.
